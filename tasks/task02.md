## 2.1. Уточнённая постановка задачи (`problem-definition`)

Используй следующие подтверждённые пользователем требования как источник истины для продуктовой постановки, профиля кандидата, конфигурации и критериев приёмки. Не позволяй LLM или значениям по умолчанию незаметно менять эти параметры.

### Цель продукта

Ежедневно собирать и анализировать актуальные вакансии Go-разработчика, доступные кандидату, который ориентируется на junior-позиции. Система должна выдавать проверяемый отчёт на русском языке, отделять обязательные условия от предпочтений и не выдавать неподтверждённые сведения за факты.

### Обязательные условия поиска

1. **Формат и география:** удалённая работа, доступная кандидату, либо гибридная работа в Санкт-Петербурге. Офисная работа без удалённого/гибридного формата не соответствует критерию. Для remote вакансий с ограничениями по стране, региону или часовому поясу проверяй, доступны ли они кандидату; если установить это нельзя, статус — `needs_clarification`.
2. **Минимальная зарплата:** не менее **119 000 RUB в месяц на руки (net)**. Это обязательный критерий, а не предпочтение.
3. **Уровень кандидата:** Junior. Приоритет отдаётся вакансиям, доступным junior-кандидатам. Не придумывай опыт работы, годы коммерческого стажа, уровень английского, специализацию или технологические навыки — они не предоставлены. Не делай окончательный вывод о соответствии по одному названию грейда; анализируй реальные требования вакансии и отмечай неизвестные данные профиля.
4. **ДМС:** необязательное преимущество, не обязательный фильтр. Подтверждённый ДМС повышает оценку; отсутствие ДМС не исключает вакансию, а неизвестность должна обозначаться отдельно.
5. **Интересность работы:** важный предпочтительный критерий. Оценивай по конкретным техническим задачам, стеку и ответственности, указанным в источнике; не выдумывай обязанности.

### Правило оценки net salary

Порог `119000 RUB/month net` нельзя считать выполненным только потому, что в объявлении указано `119000 RUB gross`, просто число `119000`, либо сумма без понятной периодичности/налогового статуса. Если источник указывает gross, неизвестный tax basis, другой период выплаты или диапазон, для которого соответствие net-порогу нельзя достоверно установить, зафиксируй исходные сведения и статус `needs_clarification`. Не пересчитывай gross в net без отдельно утверждённой, документированной и протестированной модели налоговых расчётов для применимой юрисдикции. Не исключай вакансию окончательно только из-за нехватки данных; исключай её, если подтверждённые сведения доказывают нарушение обязательного условия.

### Локальная LLM

По умолчанию используй локальную модель через Ollama. Система должна иметь конфигурируемые URL/имя модели, проверку доступности и понятную диагностику. Платные облачные API не должны использоваться автоматически как fallback. Подключение облачного провайдера допускается только при явном включении пользователем в конфигурации; секреты не хранятся в репозитории. Если Ollama недоступна, используй только предусмотренный безопасный детерминированный fallback или заверши соответствующий этап с явным статусом; не имитируй успешный LLM-анализ.

### Частота поиска

Целевая частота — ежедневно. Должен существовать документированный способ настроить и запустить ежедневное выполнение, а также сохранить ручной запуск. Не запускай бесконтрольный фоновый процесс самовольно. Если в текущем проекте нет scheduler, реализуй повторно используемую команду ежедневного поиска и документированную настройку внешнего планировщика (например, cron или Windows Task Scheduler). Повторный запуск не должен плодить дубликаты или терять историю.

## 3. Приоритет P0 — корректность источников и подтверждение фактов

### 3.1. Устранить противоречие между официальным API и scraping

Сейчас описание проекта называет официальный API, но отчётный pipeline `VacancyDiscoveryAgent` использует `HHAdapter.scrape`; `HHWebScraper` применяет `curl_cffi` с имитацией TLS fingerprint браузера и описывает обход anti-bot-защиты. Custom agent в `.github/agents/hh-learning-analyst.agent.md`, напротив, запрещает автоматизированный HTML scraping и требует официальный API.

Приведи реализацию к одному прозрачному режиму:

- Для автоматического сбора используй документированный официальный API и адаптер с понятными тайм-аутами, ограничением скорости запросов и обработкой HTTP 401/403/429/5xx.
- Не используй имитацию браузерного отпечатка, обход CAPTCHA/anti-bot, ротацию IP или другие механизмы обхода ограничений доступа. Не советуй обходить защиту в документации.
- Если официальная интеграция требует OAuth, документируй получение токена и работу через переменные окружения. Не сохраняй секреты в репозитории, отчётах или логах.
- Требуй явного первоначального включения сетевого поиска пользователем через конфигурацию/команду установки режима. После такого разрешения ежедневный scheduler может выполнять поиск автоматически в рамках выбранных источников и лимитов; не спрашивай подтверждение перед каждым ежедневным запуском. Если разрешение не включено, отсутствуют обязательные credentials или источник изменил требуемые условия доступа, не выполняй соответствующий сетевой запрос и объясни причину. Сохраняй диагностические сведения без секретов.
- Не подменяй ошибку источника фиктивными вакансиями или незаметным fallback на другой сетевой метод.
- Фикстуры разрешены только в явно обозначенном тестовом режиме и должны быть помечены в metadata как synthetic/fixture data.

Если текущий публичный API не даёт нужных полей или доступа, зафиксируй ограничение, сохрани рабочий fixture-режим и не утверждай, что такой факт был проверен в реальной вакансии.

### 3.2. Реализовать настоящую проверку вакансии

`VacancyVerificationAgent` сейчас считает URL подтверждением источника, но не проверяет доступность карточки/статус вакансии и не прикладывает доказательства извлечённых фактов.

- Используй детали вакансии из официального API или разрешённого источника для проверки статуса и актуальности. Не выполняй произвольное открытие URL из недоверенного содержимого без проверки разрешённого домена.

## 4. Приоритет P0 — исправить рейтинг и обязательные критерии

### 4.1. Зарплата

В `ScoringCalculator._score_salary` используются фиксированные приближения USD→RUB и EUR→RUB, игнорируются период выплаты и неопределённость налогового статуса. При отсутствии нижней границы зарплаты код также подставляет `0` через `salary.from_amount or 0`, что может занизить балл и исказить классификацию. Пользователь уточнил, что порог 119 000 рублей означает сумму **на руки (net) за месяц**.

Сделай нормализацию зарплаты детерминированной и проверяемой:

- Сохраняй исходный текст и исходные поля зарплаты.
- Для сравнения с порогом **119 000 RUB/месяц net** учитывай валюту, период выплаты и tax basis. Не сравнивай годовую/часовую сумму с месячным порогом без явно реализованной и протестированной конвертации.
- Удали захардкоженные курсы валют. Используй датированный курс из явно заданного надёжного источника либо оставляй вакансию в статусе «Требует уточнения». Даже при известном валютном курсе конвертация gross/net должна выполняться отдельно.
- Не вычисляй net из gross без отдельного, задокументированного и протестированного режима расчёта для применимой юрисдикции. По умолчанию не предполагай налоги и не считай gross-предложение прошедшим обязательный net-порог.
- Отдели подтверждённое несоответствие от недостатка информации. Рекомендуемая логика для нижнего/верхнего предела: если подтверждённый максимум ниже порога — `not_suitable`; если подтверждённый минимум не ниже порога — критерий пройден; если диапазон пересекает порог или известен только максимум выше порога — `needs_clarification`.
- Проверь нулевые значения, `None`, отрицательные значения, перепутанные границы диапазона, неизвестную валюту и неизвестный период.

### 4.2. География и формат работы

Не оценивай соответствие только по `work_format`. Проверяй совместно формат и локацию:

- Санкт-Петербург: удалёнка или гибрид.
- Другие регионы: включать только при явно подтверждённой удалёнке, доступной кандидату.
- Если география удалённой работы или страна найма неизвестны, указывай это как неопределённость.
- Офис в Санкт-Петербурге не считать подходящим форматом, если пользователь требует удалёнку или гибрид.

Сделай функцию оценки/валидации детерминированной и покрой комбинации тестами.

### 4.3. ДМС и режим обязательности

Согласуй семантику `require_dms` между `task01.md`, `config/candidate.yaml`, моделью и рейтингом. В исходном ТЗ ДМС описан как предпочтение: отсутствие подтверждения должно уменьшать балл, но не превращать неизвестное в отрицательный факт.

- Введи однозначный параметр, например `dms_mode: prefer|required`.
- Значение по умолчанию должно соответствовать `task01.md`: `prefer` — ДМС повышает рейтинг, неизвестность требует уточнения, но сама по себе не исключает вакансию.
- Если пользователь явно включает `required`, отсутствие/отрицание ДМС должно влиять на статус отдельно от рейтинга.
- Не считать упоминание «ДМС после испытательного срока» безусловным ДМС с первого дня: сохраняй условия и примечание.
- Проверь, что параметр реально используется, загружается из конфигурации и отражён в отчёте.

### 4.4. Валидация весов

`config/scoring.yaml` загружается с нормализацией суммы весов, но нужно также проверять типы, отрицательные значения, отсутствие ожидаемых ключей и некорректные значения. При неверной конфигурации выдай диагностическую ошибку или безопасный fallback с предупреждением. Добавь тесты.

### 5.2. Fallback LLM для каждой вакансии

В `GoTechnicalAnalyst` и `CareerFitAnalyst` при частичном успехе LLM весь batch сейчас может завершаться без эвристического fallback для отдельных вакансий, где LLM завершилась ошибкой.

- Применяй fallback индивидуально к каждой вакансии, для которой LLM вернула ошибку, пустой ответ или некорректный JSON.
- Валидируй типы и диапазоны полей результата LLM; не принимай произвольные значения и списки неправильного формата.
- Не заменяй отсутствие данных фиктивной уверенностью. По возможности возвращай отдельную оценку уверенности/полноты.
- Добавь тест: одна вакансия проходит через LLM, другая падает, третья получает невалидный JSON — результат для всех должен быть полным и помеченным корректным способом.

### 5.3. Эффективные лимиты

- Сделай `agent_timeout_seconds` действительно работающим. Текущий расчёт timeout, пропорциональный количеству вакансий, не равен реальному лимиту длительности всего этапа.
- Установи понятные верхние пределы на число вакансий, вызовы LLM, попытки повторов, сетевые запросы и общую длительность запуска.
- Не допускай, чтобы «timeout» возвращал управление пользователю, а фоновые задачи продолжали бесконтрольно выполняться.
- Сохраняй метрики времени по этапам и причину тайм-аута.

### 5.4. QA должен действительно проверять и исправлять процесс

Сейчас при QA-ошибке оркестратор повторно вызывает ранжирование, но не гарантирует обновление категорий отчёта/сводки и не выполняет полноценную проверку результата после исправления.

Реализуй конечный цикл:

1. Построить report.
2. Проверить факты, источники, статусы, дубликаты, зарплаты, обязательные критерии, сводные счётчики и валидность структуры JSON/Markdown.
3. Если есть исправимая проблема — изменить данные только на основе имеющихся доказательств и пересобрать рейтинг и отчёт.
4. Повторно провести QA.
5. Если проблема осталась — сохранить список ошибок, явно отметить QA как неуспешный/частичный и не выдавать отчёт за прошедший проверку.

QA не должен изобретать факты и не должен считать любой непустой URL доказательством доступности вакансии. Пустой поиск не обязан считаться дефектом: корректно сформированный отчёт с нулём вакансий может быть успешным результатом при недоступности источника, если ограничение указано явно.

## 6. Приоритет P1 — закончить продуктовую функциональность

### 6.1. Поиск из нескольких источников

Текущее описание discovery указывает на один реальный источник — hh.ru — и fixtures; второй независимый реальный источник не подключён, а `HHAdapter.from_public_urls()` является заглушкой.

- Создай общий интерфейс адаптера источника с едиными методами поиска, получения карточки и нормализации.
- Реализуй не менее двух независимых разрешённых источников, если у них доступны официальные API/разрешённый публичный интерфейс. Предварительно проверь условия использования и лимиты каждого источника.
- Если второй источник требует недоступной авторизации, оставь полноценный интерфейс и fixture-контракт, задокументируй реальное ограничение, но не заявляй, что независимый источник реализован.
- Ошибка одного источника не должна стирать результаты другого; отчёт должен показывать, какие источники успешно отработали, а какие нет.
- Сохраняй исходный источник, URL и ID вакансии для каждой записи.

### 6.2. Дедупликация

Сейчас дедупликация выполняется по точному URL. Добавь безопасную многоступенчатую дедупликацию:

1. Канонизация URL и удаление известных tracking-параметров.
2. Совпадение source ID, если источник тот же.
3. Поиск вероятных дублей между источниками по нормализованным работодателю, названию, локации и описанию.
4. Не объединять две похожие, но разные вакансии автоматически при недостаточной уверенности: помечать для проверки.
5. Сохранять альтернативные URL и историю источников.

### 6.3. Профиль и частота поиска

- `ConfigLoader` должен загружать все поддерживаемые поля `CandidateProfile`, включая `search_frequency`, либо явно документировать поля, которые используются только в ручном режиме.
- Исправь разбор зарплаты из свободного запроса: поддержи форматы вроде `от 150 000`, `150 тыс. руб.`, `от 119 т.р.` и не интерпретируй произвольное число из текста как зарплату.
- Сохраняй пользовательские критерии и не позволяй LLM незаметно менять обязательные параметры; неизвестные поля и противоречия должны быть явно видимы.
- Если scheduler не входит в текущую архитектуру, не создавай скрытый фоновый процесс: поддержи частоту в конфигурации и документируй запуск через системный планировщик (Windows Task Scheduler и cron) с возможностью ручного запуска.

### 6.4. Карьерное соответствие

`CareerFitAnalyst` должен сравнивать вакансию с известными данными `CandidateProfile`, а не выводить соответствие только из грейда по названию вакансии.

- Передавай профиль кандидата в анализ.
- Если опыт, грейд, специализация или стек кандидата неизвестны, не делай вывод о конкретном match/mismatch.
- Отделяй требования вакансии от фактов о кандидате.
- В карточке показывай, что известно, что неизвестно, потенциальные риски и вопросы рекрутеру.

### 6.5. История и обнаружение новых вакансий

- Сохраняй метаданные каждого запуска: исходный запрос, параметры фильтрации, источники, время поиска, время проверки, число найденных/проверенных/уникальных записей и ошибки по источникам.
- Сравнивай с предыдущими успешными запусками: новые вакансии, изменившиеся условия и вакансии, которые больше не обнаруживаются. Не объявляй вакансию закрытой только на основании отсутствия в результатах поиска.
- В отчёте явно выделяй новые вакансии и требует ли позиция перепроверки.

## 7. Приоритет P1 — согласовать custom agent и документацию

В текущем репозитории README и `.github/agents/hh-learning-analyst.agent.md` сохраняют старый сценарий prompt-engineering/vibe-coding поиска и правила, которые противоречат задаче Go-вакансий.

- Создай отдельного workspace-агента для поиска и анализа вакансий Go-разработчика с корректным описанием, входами, параметрами, источниками, требованиями к доказательствам и правилами безопасности.
- Сохрани старый агент/команды для старого сценария, если они нужны, но чётко ограничь область их применения. Не позволяй им менять критерии, фильтры или инструкции Go-системы.
- Обнови верхнюю часть README: основное назначение проекта — поиск вакансий Go-разработчика; опиши действительный источник данных и доступные режимы. Удали противоречивые заявления, команды и рекомендации, которые больше не соответствуют коду.
- Обнови `docs/architecture.md`, `docs/agents.md`, `docs/operations.md` и пример конфигурации после изменения фактического поведения. Документация должна точно отражать, какие агенты используют LLM, какие проверки реально работают и какие источники доступны.

## 8. Требования к отчёту

Markdown и JSON должны содержать одинаково согласованные данные и включать:

- ID запуска, время запуска/завершения, период и параметры поиска;
- источник каждого результата, состояние источника и ограничения сбора;
- найдено, проверено, уникально, подходит, требует уточнения, не подходит;
- статус QA и обнаруженные замечания;
- зарплату с валютой, периодом и tax type либо указанием неизвестности;
- формат и географию работы;
- статус ДМС с подтверждающим свидетельством либо явным отсутствием подтверждения;
- статус активности/проверки вакансии;
- объяснение каждого компонента рейтинга и итогового балла;
- причины исключения и признаки неопределённости;
- ссылки и краткие доказательства ключевых фактов;
- отдельные категории «Подходят», «Требуют уточнения» и «Не подходят»;
- лучшие варианты, вопросы работодателю, следующие действия и новые вакансии относительно предыдущего успешного запуска.

Проверь, что сериализация dataclass включает все заявленные поля отчёта: не полагайся на динамические атрибуты, которые `dataclasses.asdict()` не сериализует. Экранируй `|`, переводы строк и Markdown-разметку в значениях таблиц, чтобы данные вакансий не ломали отчёт.

## 9. Обязательные автоматические тесты

Добавь тесты к новой мультиагентной системе, а не только к legacy CLI. Тесты должны работать без сети и платных API, используя фикстуры и моки.

Минимальный набор:

1. Официальный API-адаптер: построение запроса, нормализация, пагинация, дедуп по source ID.
2. Источник недоступен/401/403/429/5xx/timeout; корректное ограничение повторов.
3. Отсутствие URL, невалидный URL, недоступная карточка и закрытая вакансия — разные статусы.
4. Evidence для зарплаты, ДМС, формата, региона и даты публикации.
5. Синтетическая fixture явно помечена и не выдаётся за реальную вакансию.
6. Разбор зарплаты `119 т.р.`, `150 тыс. руб.`, `150 000`, диапазона и неизвестного формата.
7. Порог зарплаты: ниже/выше 119 000 RUB в месяц net, диапазон пересекает порог, только верхняя граница, неизвестная валюта, годовая/месячная выплата, gross, net, неизвестный tax basis; gross не должен автоматически проходить net-порог.
8. Конвертация валюты по датированному источнику либо переход к `needs_clarification` без курса.
9. География × формат: СПб hybrid/remote, СПб office, другой регион remote/office, регион неизвестен.
10. ДМС: confirmed, not mentioned, unknown, после испытательного срока; оба режима `prefer` и `required`.
11. Веса рейтинга: корректные, отсутствующие, отрицательные, неправильные типы, сумма не равна 1.
12. Дедуп exact URL, tracking URL, общий source ID и похожие вакансии из разных источников.
13. LLM partial failure: успешный ответ, исключение, пустой ответ и невалидный JSON в одном наборе вакансий.
14. Orchestrator: ошибка одного источника, ошибка одного агента, ограниченный retry, эффективный timeout и сохранение частичных результатов.
15. QA: выявление ложного подтверждения источника, дублей, некорректных статусов, несовпадения счётчиков и несогласованности отчёта; повторная проверка после исправления.
16. Markdown/JSON сериализация: ключевые поля, даты/enum, метаданные, escaping таблиц и соответствие между форматами.
17. История запуска: обнаружение новой/изменённой вакансии и отсутствие ложного вывода о закрытии.
18. Prompt injection на русском и английском; текст вакансии не меняет системные инструкции и не запускает инструменты.
19. Legacy-тесты и старые команды остаются работоспособными либо документированно мигрированы.

Не заявляй, что тесты пройдены, если команда фактически не была запущена.

## 10. Рекомендуемый порядок реализации

1. Исследовать существующие файлы и тесты, записать фактический baseline.
2. Исправить source adapter и проверку достоверности.
3. Исправить модели зарплаты, географии, ДМС, рейтинга и статусов.
4. Исправить контракты агентов, fallback и QA-цикл.
5. Добавить многоисточниковый интерфейс и корректную дедупликацию.
6. Довести профили, историю запусков и расписание.
7. Отделить Go-agent от старого workspace-агента, обновить документацию.
8. Выполнить полный тестовый прогон и ручную проверку fixture-сценария.

Не пытайся выполнить параллельно много независимых изменений, если они затруднят диагностику. После каждого этапа запускай соответствующие тесты.

## 11. Критерии приёмки

Работа готова только если выполнено всё применимое ниже:

- [ ] Код изменён в актуальной ветке `dev`; пользовательские изменения сохранены.
- [ ] Основной pipeline не использует обход anti-bot и использует документированный разрешённый способ получения данных.
- [ ] Реальная проверка вакансии отделена от проверки наличия URL.
- [ ] Ключевые факты подтверждаются источниками; неизвестные значения не превращаются в факты.
- [ ] Нет захардкоженных курсов валют и некорректного сравнения salary period/tax type; критерий зарплаты трактуется как 119 000 RUB/месяц net.
- [ ] Статус обязательных критериев отделён от общего рейтинга.
- [ ] Режим ДМС однозначен, конфигурируем и покрыт тестами.
- [ ] LLM fallback работает по каждой вакансии, логические ошибки агентов не маскируются как успех.
- [ ] Timeout, retry и QA-цикл имеют реальные границы и тестируются.
- [ ] Дедупликация не ограничена только точным URL.
- [ ] Источники подключены через общий интерфейс; статус и ошибки каждого видны в отчёте.
- [ ] Markdown и JSON отражают актуальное состояние и содержат полные метаданные.
- [ ] История запусков различает новые/изменившиеся вакансии и не делает неподтверждённых выводов о закрытии.
- [ ] Go workspace-agent и документация не противоречат реализованному поведению.
- [ ] Есть тесты перечисленных ключевых сценариев, включая ошибки и безопасность.
- [ ] Все реально запущенные тесты и их результаты указаны в финальном отчёте.
- [ ] В корне репозитория создан и заполнен `task02_report.md` с фактическим отчётом о выполненных работах; файл проверен на соответствие реальному состоянию кода и тестов.

Если какой-либо критерий блокируется недоступностью внешнего API или отсутствием credentials, реализуй тестируемый интерфейс и fixture-режим, задокументируй ограничение и пометь соответствующий критерий как невыполненный, а не как выполненный.
